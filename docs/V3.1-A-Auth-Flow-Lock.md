## 2. 已有账号验证码登录

```text
输入邮箱
→ sendOtp intent = sign-in
→ shouldCreateUser = false
→ 输入六位验证码
→ verifyOtp
→ 已设置密码：进入 AppShell
→ 未设置密码：进入首次设置密码门禁
```

- 未知邮箱不得在登录流程中静默创建账号。
- 页面应以温和文案引导用户进入显式注册页。
- 发送成功后，同一认证卡片切换到验证码输入状态：脱敏邮箱、6 位验证码输入、重新发送倒计时和更换邮箱入口。
- 验证码固定为 6 位数字；错误、过期、网络失败和重复请求均须通过统一 Auth facade 映射为温和、可行动的提示。

## 3. 显式注册

```text
从登录页进入 RegisterPage
→ sendOtp intent = sign-up
→ shouldCreateUser = true
→ 输入六位验证码
→ verifyOtp
→ Session 建立
→ 首次设置密码
→ 进入 AppShell
```

- 注册与登录共用普通 OTP 能力和验证码视觉交互，但必须传递不同 intent。

- 已有账号的注册冲突遵循 Architecture 锁定的安全、温和引导；不得通过额外探测枚举账号。

## 4. Recovery OTP 密码重置

Recovery 的唯一正式产品流程为：

```text
recovery-email-entry
→ recovery-requesting
→ recovery-code-entry
→ recovery-code-verifying
→ recovery-password-required
→ recovery-password-updating
→ recovery-signout-pending
→ recovery-complete
→ password-login
```

用户可理解的流程为：

```text
输入邮箱
→ 发送六位恢复验证码
→ 输入验证码
→ 验证 Recovery Session
→ 设置新密码
→ local signOut
→ 返回密码登录
```

正式 facade action 与 Supabase 语义固定为：

```text
sendRecoveryOtp(email)
→ resetPasswordForEmail(email)
→ 不传 redirectTo

verifyRecoveryOtp(email, code)
→ verifyOtp({
     email,
     token: code,
     type: "recovery"
   })

updateRecoveryPassword(password)
→ updateUser({
     password,
     data: { password_set: true }
   })
```

Recovery OTP 验证成功后，SDK 可能产生 `PASSWORD_RECOVERY`。该事件必须由 Recovery owner 消费，不得进入普通 `authenticated` 或 AppShell。

密码更新成功后的唯一完成策略为：

```text
USER_UPDATED
→ Recovery owner 消费
→ recovery-signout-pending
→ auth.signOut({ scope: "local" })
→ 清除 Recovery marker
→ guest
→ password-login
```

成功文案方向：

```text
密码已经更新，可以重新登录了
```

禁止：

- `resetPasswordForEmail + redirectTo → ConfirmationURL → 点击邮件链接 → 浏览器回跳` 作为正式产品流程；
- 将 `{{ .ConfirmationURL }}` 作为主要用户操作；
- Recovery Session 直接进入 AppShell；
- global signOut；
- 自动登录；
- 将 Recovery Session 当普通登录 Session；
- `USER_UPDATED` 触发普通 authenticated。

Recovery 失败、marker 损坏、事件无法归属或 local signOut 失败时，必须保持 fail-closed。local signOut 失败时 marker 和 Recovery lock 保留，只显示 AuthShell Recovery fatal/retry，不显示完成或普通密码登录流程。

### 4.1 Recovery 与页面状态边界

顶层 AuthState 只允许表达 Recovery 的稳定安全状态：

- `recovery-password-required`：仅当前页面生命周期中双证据成立的 owner；
- `recovery-blocked`：observer 的正式顶层安全状态；
- `recovery-signout-pending`；
- `recovery-fatal-error`。

其中 `recovery-blocked` 只能显示 AuthShell 内的安全说明：当前 Profile 正在 Recovery、当前标签不是 owner。它不显示密码输入，不允许 `updateRecoveryPassword`、local signOut、普通 authenticated reconciliation 或成为第二个 owner，且始终 `AppShell=false`。

以下属于正式 Recovery 页面或临时 Probe 的局部状态，不进入顶层 AuthState：

- `recovery-email-entry`；
- `recovery-requesting`；
- `recovery-code-entry`；
- `recovery-code-verifying`；
- `recovery-password-updating`；
- `recovery-complete`。

邮箱、OTP、密码和确认密码只允许存在当前表单局部 state / 原生输入控件，必须在提交、成功、页面切换、退出和卸载时清理。

## 5. 首次设置密码与密码登录

### 5.1 首次设置密码

普通 OTP 登录、注册 OTP 验证或正常初始化时，若 `password_set !== true`：

```text
authenticated-needs-password
→ 首次设置密码门禁
→ 设置成功
→ authenticated
→ AppShell
```

首次设置密码不是可跳过推荐项。用户仅可明确选择“退出当前账号”，且退出使用 local signOut。

Recovery 密码更新不是首次设置密码；Recovery 成功后必须 local signOut 并返回 PasswordLogin，不得复用“设置成功即进入 AppShell”的完成语义。

### 5.2 密码登录

```text
密码登录成功
→ 直接 authenticated
→ AppShell
```

`password_set` metadata 仅为产品体验标记：密码登录成功后可 best-effort 补写 `password_set:true`；补写失败不阻断进入 AppShell、不强制再次设置密码，也不得将用户降级为 `authenticated-needs-password`。

邮箱验证码登录和邮箱密码登录长期并存。

## 6. Profile 共享 Recovery marker 与多标签页

Recovery marker 使用 Profile 共享 `localStorage`；当前标签身份使用 `sessionStorage`。不得使用 `sessionStorage` 作为唯一 Recovery marker。

Profile 共享 marker 只能包含以下非敏感字段：

- `version`；
- `flowId`；
- `ownerTabId`；
- `phase`；
- `createdAt`；
- `expiresAt`。

marker 不得包含：

- email；
- userId；
- OTP；
- password；
- token；
- cookie；
- session；
- recovery URL。

marker 只证明当前浏览器 Profile 存在一个 Recovery flow，用于跨标签协调与 AppShell 安全锁。它不是身份凭据、不是 Session 认证证据，不能证明 Session 属于哪个邮箱或用户，也不能在刷新后重建 owner 权限。Supabase Session 是唯一 Auth 身份来源；Session 同样不能绕过 Recovery marker / lock 直接进入 AppShell。

不新增数据库字段、不新增服务端 Recovery 表、不新增第二个 Auth Client、不新增第二个 Auth subscription。具体 marker key、schema、expiry 数值、storage helper、原子更新与 corruption parsing 由后续 Execution Plan 锁定；本 Architecture 不擅自写未经代码核验的具体常量。

### 6.1 Recovery owner admission：不可违反的 Session ID 规则

Recovery marker 只协调 Profile flow 与锁定 AppShell；发送邮件、进入验证码页、marker、Promise 或 `PASSWORD_RECOVERY` event 单独都不授予密码更新权限。

只有当前 document 的 active Recovery verify attempt 同时满足下列产品与安全条件，才可进入 `recovery-password-required`：

1. `verifyRecoveryOtp` Promise 和 `PASSWORD_RECOVERY` event 都返回非空 `sessionId`；
2. 两个 `sessionId` 完全相等，且 Promise / event user ID 完全相等；
3. 当前 flow / attempt / owner-candidate lineage 仍有效，当前 marker 真实重读后仍为 exact owner marker，operation 未 settled；
4. `getCurrentUser()` 最终确认当前 user 存在且 ID 匹配。

`sessionId` 只用于 provider event correlation，不是 owner authority、身份授权、marker、storage / Cookie / URL 值、UI state、日志、错误 payload 或 token 替代品。duplicated 或重新挂载的 tab 即使共享 session ID，也不得恢复旧 owner。实现层的 ref、generation、revision、timer、callback 与 settlement 规则以 Architecture / Execution Plan 为准。

### 6.2 Ownership loss 与一次性密码更新

每个 Recovery Session 最多一次 password update；成功的 update 后必须 local signOut，且只有 local signOut 成功后才能清理 exact current marker。`SIGNED_OUT` 可以没有 Session，因此它只能收敛既有本地 completion 的结果，不能独立授权完成。

foreign、changed、absent、invalid、expired、storage unavailable 或 exact marker reread conflict 都立即撤销 owner destructive authority。observer、duplicated/reloaded document、owner candidate、identity-uncertain document 和失去 marker ownership 的 document 必须保持 `recovery-blocked` 或 `recovery-fatal-error`、`AppShell=false`，不得 update、启动 owner completion signOut、清/覆盖 marker 或使用 stale marker snapshot。

唯一 cleanup 例外是当前 document 自己发起的 verify operation 在已 timeout/stale 后 Promise 明确成功、可能由该 document 建立了 Recovery Session。它是无 marker authority 的 own late-success Session cleanup：不授予 owner、不依赖 persisted ownerTabId、不清 foreign marker，且始终 `AppShell=false`。

### 6.3 刷新、observer 与用户控制

刷新、复制、Strict Mode replay 或重新挂载不得恢复旧 Recovery owner authority。observer 只能保持 blocked，并等待 `SIGNED_OUT` 或权威 current Session=null 收敛；不得自行 destructive signOut。

用户保有密码提交、明确取消 / 放弃与正常“退出当前账号”的最终决定权。恢复成功后固定 local signOut 并返回 password-login；Recovery Session 永不进入 ordinary `authenticated` 或 AppShell。

**AppShell gate：** 只有 `authState.status === "authenticated"`，且不存在 Recovery marker、Recovery lock、Recovery attempt、`recovery-password-required`、`recovery-blocked`、`recovery-signout-pending`、`recovery-fatal-error` 或归属不确定时，才允许进入 AppShell。任何 Recovery 信号或 marker 读取失败均为 `AppShell=false`。

## 7. 退出当前账号

“退出当前账号”固定为 local signOut：

```ts
auth.signOut({ scope: "local" })
```

- 仅退出当前浏览器 Session；
- 同一浏览器中共享该 Session 的标签页通过 `SIGNED_OUT` 收敛为 guest；
- Recovery observer、duplicated/reloaded document、owner candidate、identity-uncertain document 和失去 marker ownership 的 document 不得因 Recovery event 或 marker 状态自行 signOut，也不得销毁 owner Session；唯一例外仅为当前 document 自己的 late successful verify Promise 所需的无 marker authority cleanup；
- marker 与 Recovery lock 只能在该 signOut 成功后清除；失败时保留并进入 `recovery-fatal-error`，只允许重试 signOut；
- 其他浏览器 Profile 的独立 Session 不受影响；
- 其他设备上的独立 Session 不受影响；
- 本阶段不实现“退出所有设备”，不得默认使用 global scope 或未指定 scope 的 `auth.signOut()`。

Recovery update 成功后的 local signOut 是产品流程的一部分，不是可选清理动作。
